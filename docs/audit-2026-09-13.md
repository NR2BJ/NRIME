- `Shift 누름 -> 문자 누름 -> Shift 뗌`이라는 같은 입력열은 빠른 전환 의도와 실제 대문자/쌍자음 의도 모두에서 나올 수 있다. 권한 확대 없이 개선할 수는 있지만, 타이밍만으로 의도를 100% 판별한다는 약속은 불가능하다.
- 버퍼는 한 글자, 제한된 겹침, 명확한 종료 규칙으로 유지한다. 다른 modifier, 반복, 두 번째 문자, 포커스 변경, 후보 상태, 키 이벤트 누락을 모두 검사한다. 전역 이벤트 탭이나 키 전체 가로채기를 기본 해결책으로 삼지 않는다.
- 현재 reset은 pending letter를 버린다. 포커스 종료 직전에 이미 소비한 글자를 잃는 경계도 소유자/종료 순서 검사에 포함해야 한다.

### Firefox와 웹사이트 차이

Firefox Cocoa 구현은 조합이 활성화된 키를 `interpretKeyEvents` 전에 processed key로 전달하는 경로를 가진다. 또한 키 처리 시작 당시 조합 여부를 저장해 뒤쪽 keypress 생성 조건에 사용한다. IME가 처리 중 확정해도 이미 보낸 DOM keydown이 일반 키로 바뀌지는 않는다. [Firefox TextInputHandler.mm](https://searchfox.org/firefox-main/source/widget/cocoa/TextInputHandler.mm)

Chromium 구현에도 기존 marked text 여부를 저장하고, composition 관련 키와 commit/edit command를 나누어 전달하는 처리가 있다. 단순히 insertText가 반환됐다는 것과 renderer가 모든 이벤트를 처리했다는 것은 다르다. [Chromium Cocoa 입력 구현](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/app_shim_remote_cocoa/render_widget_host_view_cocoa.mm)

따라서 같은 Firefox에서도 사이트가 `isComposing`, compositionend, keydown의 preventDefault 등을 다르게 취급하면 결과가 달라질 수 있다. 이것은 소스에서 도출한 설명이며 **Gemini 현재 웹사이트의 정확한 이벤트열을 직접 관측한 결과는 아니다**.

### 사용할 수 있는 정보와 없는 정보

- 로컬 SDK의 IMKTextInput은 marked/selected range, insertText, setMarkedText 등 문서 인터페이스를 제공한다. 웹사이트의 Enter 정책이나 JS 이벤트 처리 완료를 조회하는 공개 인터페이스는 없다.
- AppKit NSResponder의 doCommandBySelector를 IMKTextInput client의 보장된 원격 메서드로 취급하면 안 된다. 같은 이름의 IMKInputController 메서드도 client의 편집 명령 전송 수단과는 다르다.
- responds(to:)나 supportsProperty만으로 해당 웹 에디터의 줄바꿈 의미를 자동 분류할 수 없다.
- AX로 좌표/텍스트 일부를 조회할 수 있다는 것 역시 compositionend 처리 완료 확인과 동의어가 아니다. 매 키마다 AX 조회/재시도하거나 문자 삽입으로 호환성을 시험하는 탐지는 하지 않는다.
- fcitx5-macos의 commit/preedit 갱신 순서와 상태 소유 방식은 참고할 만하다. 다만 dummy preedit 경로에도 클라이언트별 조건이 있어서 그대로 가져온다고 무예외 호환성이 보장되지 않는다. [fcitx5-macos frontend](https://github.com/fcitx/fcitx5-macos/blob/master/macosfrontend/macosfrontend.swift)

## 최적화와 정리 순서

1. **동작 정합성 먼저**: A1-A7의 입력 순서/세션/관찰 문제를 회귀 테스트로 고정한다. 성능 개선을 이유로 타이머를 더 늘리거나 입력 경로를 새로 갈아엎지 않는다.
2. **중복 키 재전송 통합**: KoreanEngine, JapaneseEngine, KeyEventReposter의 중복 구현은 하나의 컨트롤러 소유 전달 지점으로 모은다. 단순 함수 추출만으로 대상/순서 문제는 해결되지 않는다.
3. **설정 읽기 캐시**: 일본어 설정은 이미 캐시하지만 shortcut은 여러 판정에서 JSON을 반복 decode한다. 설정 변경 시 교체하는 불변 snapshot을 고려한다. 지연량은 계측 전이므로 이것이 체감 지연의 주원인이라고 단정하지 않는다.
4. **후보 표시 중복 갱신 감소**: 엔진 show와 컨트롤러 show가 중복될 수 있고 매 show마다 폭 측정/좌표 조회를 한다. 후보 목록/페이지/선택 변화별로 갱신 범위를 나눈다. 좌표 갱신 자체를 생략해 커서 추적을 깨뜨리면 안 된다.
5. **blocking 경로 관리**: Mozc C 래퍼가 정상이어도 IPC timeout/서버 시작 대기는 여전히 동기 경로에 있다. 현재 정상 변환을 재작성하지 않고 장애 시 호출 횟수/최대 대기/원문 보존을 별도 검사한다. 기존 세션 생성과 서버 launch 직렬화 수정은 유지한다.
6. **진단 경량화**: DeveloperLogger의 파일 쓰기는 이미 별도 queue다. 과거 문서의 "동기 파일 쓰기"를 현재 결함으로 재보고하지 않는다. 다만 비활성 로그의 metadata 계산, 중복 좌표 조회, 핫패스의 설정 decode 비용은 측정할 수 있다.

## 구현 제안: 단계별로 하나씩

### 1단계: 호스트를 바꾸지 않는 내부 수정

- 키 관찰과 처리 우선순위 분리, modifier별 gesture 상태, 후보 Shift+Enter 처리 누락, 후보 종료, 표시 문자열 확정을 수정한다.
- 타이밍 임계값/전역 권한/후보 좌표/Mozc 전송은 이 단계에서 유지한다.
- 성공 조건: A3-A7에 해당하는 6개 재현의 기대 결과 충족, 기존 한글/일본어/단축키 테스트의 회귀 없음, 일반 Enter 후보 확정 의미 유지. A1/A2의 소유권 검사는 2단계에서 함께 해결한다.

### 2단계: 확정과 후속 동작의 소유권

- 엔진의 Bool만으로는 `확정했는지`, `원래 키를 넘겨야 하는지`, `후속 동작이 이미 예약됐는지`가 드러나지 않는다. 내부 결과 타입으로 구별하고 IMKit Bool 반환은 컨트롤러 경계에서 한 번 정한다.
- 후속 동작에는 세션 세대/원래 client/동작 종류/처리 여부를 붙인다. 클라이언트 조회는 가능한 공개 범위에서 하되, 같은 앱의 다른 웹 필드까지 영구 식별할 수 있다고 가정하지 않는다.
- `줄바꿈 대기 중 새 글자`, `두 번 Shift+Enter`, `모드 변경`, `클릭`, `앱 변경`, `보안 입력 전환`의 정책을 먼저 정한다. 새 글자를 받아놓고 이전 insertText가 새 marked text를 교체하는 상태를 금지한다.
- 전역 CGEvent 재전송이 불가피한 실험은 원래 대상/현재 포커스 확인, 중복 방지, 키 눌림/해제 정합성을 갖춰 별도 비교한다. 이것만으로 renderer 적용 완료를 보장하지는 않는다.
- 성공 조건: A1/A2를 포함한 8개 재현 전체의 기대 결과 충족. 실제 호스트 호환성 완료 여부는 3단계에서 별도로 판정한다.

### 3단계: 실제 편집기 검증 후 호환 경로 선택

- 로컬 textarea/contenteditable/조합 중 keydown 무시/직접 Enter 처리 편집기를 만들어 DOM 이벤트를 수집한다. 페이지 종류를 제품의 예외 목록으로 넣는 것이 아니라 재현 fixture로 사용한다.
- 기록: keydown/keyup, compositionstart/update/end, beforeinput/input의 순서, isComposing, shiftKey, keyCode, defaultPrevented, 최종 문자열과 선택 범위. 개인정보가 없는 정해진 테스트 문구만 사용한다.
- 기본 macOS 입력기를 대조군으로 같은 실제 키 입력을 비교한다. JavaScript dispatchEvent만으로는 macOS IMKit 흐름을 재현할 수 없다.
- 이어서 Codex와 Firefox Gemini에서 사용자가 보고한 경로를 측정한다. 현재 활성 대화에 시험 입력/전송하지 않는다.
- 비교 기준: 글자 유실/중복 없음, 의도치 않은 전송 없음, 줄바꿈 정확히 한 번, 다음 글자의 위치 정확, Shift 해제 시 오전환 없음, 부하 시 순서 유지.
- 범용 경로가 확인되면 기존 bundle-ID 예외를 제거한다. 확인 전에 모든 앱에 동일 workaround를 강제하지 않는다. API로 알 수 없는 정보를 "자동 감지"라고 포장하지 않는다.
